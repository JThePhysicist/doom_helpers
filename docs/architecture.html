doom_helpers / doomwad 0.1.0 · improvement stack

C4 architecture

A local Python toolkit for inspecting Doom WAD archives and editing sprite artwork through PNG atlases. This document describes the implementation including the improvement stack. See the delivery status for branch and validation details.

Level 1 · System context

The user operates the toolkit on local files. A separate image editor changes atlas artwork; a separate Doom engine consumes the rebuilt mod. There are no application servers, databases, authentication services, or runtime API calls.

Mod author[Person]Inspects archives and edits sprites
Python developer[Person]Uses APIs and runs tests
↓ Invoke commands / call Python APIs
doomwad[Software system · Python]Reads WADs, decodes sprites, manages atlases, writes WADs
↕ Reads and writes local WAD, PNG, and JSON files
Image editor[External software system]Reads/writes PNG artwork
Doom engine / source port[External software system]Loads the base IWAD and output PWAD

External tools communicate through files, not a network integration. Base game WADs are supplied by the user. Packaging downloads dependencies during installation; it is outside the runtime architecture.

Level 2 · Containers

In C4, a container is an application or data store, not necessarily a Docker container. Here each command runs as a short-lived Python process. The reusable library is an in-process dependency, not an independently deployed service.

Deployment consists of a Python environment with an editable package and Pillow. pytest is a development dependency. Atlas command implementations are installed in the package; repository scripts are compatibility wrappers. No long-running process needs restarting between tasks.

ResponsibilityImplementation and boundary
Archive storageWad loads complete files into memory. The WAD header stores type, lump count, and directory offset; directory entries store byte position, size, and eight-byte name. Raw lump order is preserved except explicit edits.
Sprite codecsprites.py recognizes frame/rotation names and sprite marker ranges. Patch headers carry dimensions and signed anchor offsets; per-column posts encode palette indices with transparency represented by omitted pixels. Vanilla encoding limits height to 255; the explicit source-port profile supports relative posts and taller images.
Palette mappingPalette reads 256 RGB colors from PLAYPAL, selects exact colors where possible, otherwise minimizes squared RGB distance. Nearest-color results are cached.
Atlas geometryShelfPacker/build_atlas sort sprites by height and fill shelves across square pages. Duplicate names are rejected. Realignment changes crop rectangles and offsets while retaining immutable nonoverlapping editing allocations, including diagonal neighbors.
Map recordsmaps.py parses THINGS, LINEDEFS, SIDEDEFS, VERTEXES, and SECTORS. DoomMap selects map-scoped records, validates references, and delegates derived geometry regeneration to an explicit external node-builder command. Hexen/UDMF remain separate unsupported formats.

decode_patch(bytes, Palette) produces a DecodedPatch. build_atlas consumes patches and produces page images plus a manifest. iter_manifest_sprites produces cropped images and offsets for encode_patch. Map record dataclasses use class-level struct formats and list conversion methods.

Manifest contract

Version 1 is a JSON object with version, atlas_size, padding, palette, pages, and sprites. Each sprite has name, page, x, y, width, height, left_offset, and top_offset. Page indices are zero based; page filenames normally resolve relative to the manifest directory. The validator enforces version 1, required fields, palette values, unique names, relative paths, page dimensions, bounds, and nonoverlapping allocations. Optional index_pages retain source color indices; patch_profile selects the codec.

Runtime view · End-to-end editing

  1. Inspect: the author discovers prefixes through the CLI; Wad reads the archive and sprite discovery scans marker ranges.
  2. Extract: the script loads source patches and PLAYPAL from the source or a separate palette WAD. It decodes RGBA images, packs pages, and saves PNGs plus the manifest.
  3. Edit: the external image editor modifies PNG pixels without rearranging pages. No application process remains active.
  4. Realign: the script loads JSON and PNGs, finds opaque bounds, and updates crop rectangles and anchor offsets. Dry-run reports changes without writing. Pages remain unchanged.
  5. Rebuild: the script crops tiles, maps opaque RGB pixels to palette indices, encodes patches, replaces existing names or inserts missing names inside a sprite range, and writes a WAD.
  6. Verify: the author inspects/re-extracts output and loads it alongside the matching base IWAD in their chosen engine.

Fresh rebuilding creates a sprite PWAD; it does not embed the original archive or palette lump. Updating an existing archive retains its type and unrelated raw lumps. Raw name-based lookups use the first occurrence, which matters for duplicate names and repeated map lump names.

Quality attributes and limits

  • Testability: generated archives and subprocess pipelines exercise the library and scripts. The suite includes property-based and regression checks, subprocess coverage, a supported-Python matrix, and isolated wheel validation. The optional engine timedemo is a separate check.
  • Portability: Python >=3.9 and Pillow are declared dependencies. No platform-specific application services are required.
  • Data integrity: negative WAD counts/sizes and truncated patch posts are rejected. Files are staged and replaced atomically; atlas batches roll back ordinary failures but are not crash-atomic. Existing CLI outputs require explicit overwrite.
  • Scope: The HTML preview is read-only. Indexed WAD reads and source-port tall patches are available. No Hexen/UDMF parser, built-in node generator, or hosted service is implemented.
  • Scale: full archives and image pages live in process memory. Shelf packing prioritizes simple placement over optimal page utilization.
